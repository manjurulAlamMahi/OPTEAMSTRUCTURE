Project Assignment

Who hands the project to whom, from the sheet down to the developer.

  1. 07 KAM Sheet

    New project logged

    Every new project starts here. It's the single source for all incoming work.

  2. PC · Project Coordinator

    Pick up & assign

    Takes the project from the sheet, checks deadline & scope, sets priority and assigns it to an Operations Manager.

  3. OM · Operations Manager

    Choose the PM

    Assigns the project to the Project Manager whose teams match the stack.

  4. PM · Project Manager

    Plan & hand out tasks

    Breaks the project into tasks and assigns them to developers.

  5. DEV · Developer

    Build

    Completes the tasks, updates GitHub and sends progress updates back to the PM.

3

Project Assignment & Handling

How a project is assigned, who owns it, how tasks are given and who handles support messages.

  1. PC · Project Coordinator

    Assign to an OM

    Assigns the new project to Operations Manager 1 or Operations Manager 2.

  2. OM · Operations Manager

    Assign to a PM

    Picks one of their 3 Project Managers whose team fits the project's stack.

  3. PM · Project Manager

    Own the project

    From here the PM handles the whole project and picks the developers from their team.

  4. DEV · Developer

    Work on the tasks

    Works only on the tasks the PM gives, on time, and reports back to the PM.

PM · Project Manager

One owner for the whole project

After assignment, everything about the project goes through its PM:

  • Client meetings
  • Client messages & progress updates
  • Assigning developers to the project
  • Giving and tracking daily tasks
  • Deadline checks until delivery
PM → DEV

Tasks are specific and written down

No vague instructions. Every task says which client, what to do and by when.

Example

Today: Client X, have the update for the Payment module ready.

What
What needs to be built or changed
Expected
What the client is looking for
Deadline
When it must be ready

When a client sends a new request, the PM writes it down in this format before giving it to a developer.

OM · Operations Manager

Support messages go through the OM

The PM does not write support messages.

  1. The PM tells the OM the project's story: status, progress, issues.
  2. The OM writes the support message from that.
  3. The OM sends it and keeps the support messages up to date.
  • One project, one PM. Meetings, client messages and updates all go through the assigned PM.
  • Clear tasks only. Developers get specific, written tasks with a deadline, not open-ended requests.
  • Support messages belong to the OM. The PM gives the story, the OM writes and sends.
4

KPI Distribution

How delivered value is shared, so everyone works for delivery, not only for the biggest project.

Now

Value follows the project you work on

Each member gets the bill of the project they worked on.

  • People chase the high-value projects instead of what the team needs
  • Nobody watches whether the project actually gets delivered, only their own part
  • A few members get a lot of value, others get very little
New

Value follows what gets delivered

Everything the Operations Manager's side delivers is added up and shared equally by all its members.

  • Everyone works for delivery, on any project
  • Everyone gets the same share, so the team works as one flow
  • Best performers get extra from a separate performance pool
  1. PM · Project Manager

    Deliver projects

    Projects are completed and delivered across the Operations Manager's teams.

  2. OM · Operations Manager

    Total delivered value

    All delivered project value under this OM is added up for the period.

  3. Performance pool

    Keep extra aside

    A separate amount is kept aside to reward the best performers.

  4. All members

    Equal share

    The delivered value is divided equally between every member under the OM.

  5. PM → Best performers

    Extra benefit

    The PM names the best performers. They get extra value from the pool or another benefit.

  • Delivery is what counts. KPI value comes from delivered projects, not from which project you were on.
  • Same share for everyone. Every member under the OM gets an equal part of the delivered value.
  • Good work is still rewarded. The PM picks the best performers for extra value or benefits.

Project Tracker & Load Balancing

One shared tool that everyone keeps updated: it shows every member's load and every project's progress, so work is assigned fairly and stuck projects are caught early.

  1. PC · Project Coordinator

    Check the tracker daily

    Every day, checks the Project Tracker for each team's and member's current load.

  2. PC · Project Coordinator

    Find the free capacity

    For a new project, finds the team with the right stack and the lowest load.

  3. PC → OM → PM

    Assign to that team

    Gives the project to that team through its OM and PM (see Work Flow 3).

  4. DEV + PM

    Keep it updated

    From then on, the developers and PM keep the project's progress up to date in the tracker.

Who uses the tracker

DEV · Developer

Updates it

Continuously updates their tasks and progress on every project they work on.

PM · Project Manager

Checks & updates it

Checks that developers have updated it, and updates the project status too.

PC · Project Coordinator

Checks load before assigning

Looks at team and member load before giving out any new project.

OM · Operations Manager

Watches progress

Follows the progress of every project and spots any that are stuck, so they can step in early.

Why we need it

Without a tracker, work piles up on the same people

Projects keep going to members who are already busy, while others have almost nothing to do. We can't see it, so we can't fix it.

  • Shows every member's load in one place
  • Makes it clear who can take a new project and who can't
  • Spreads the work evenly, so nobody is overloaded or left idle
Example · member load

Who should get the new project?

  • Member A5%
  • Member B80%
  • Member C90%
  • Member D190%

100% = full load

Member D is almost at double load while Member A is nearly free. The new project goes to Member A.

  • Check the tracker every day. The PC knows every team's load before assigning anything.
  • Lowest load first. A new project goes to the right-stack team or member with the most free capacity.
  • Always up to date. Developers and PMs update it continuously; the PM makes sure nobody skips it.

Special / Rapid Team: Audits & Stack Leadership

How the Special / Rapid Team (Stack Leaders and SQA) checks projects and leads their stack.

  1. PM or OM

    Assign an audit

    A PM or OM asks the Special Team to audit or track a specific project.

  2. SPT · Stack Leader

    Audit the source code

    Goes through the project's source code: structure, tech used and code quality.

  3. SPT · Stack Leader + SQA

    Check the real progress

    Compares the actual work with the updates on the tracker: is it really done, or only reported as done?

  4. SPT → PM / OM

    Report back

    Reports what they found to the PM or OM who asked, including any issues or fake updates.

Audit

What an audit checks

  • Source code structure
  • What they are coding with (stack, libraries, tools)
  • Code quality and standards for that stack
  • Work progress: completed or not
  • Fake or wrong updates on the tracker
Stack Leader

Meetings with their stack

Each Stack Leader represents their stack across the teams.

  • Holds meetings with all members of their stack
  • Shares updates, standards and lessons from audits
  • Helps members who are stuck
SQA

Quality checks

The SQA member in each Special Team tests the work during audits, and check important and rapid projects before they go out.

The Special Team also builds rapid and high-priority projects (see Work Flow 2).

  • Audits on request. A PM or OM assigns every audit, so the Special Team knows exactly what to check.
  • Real progress, not reported progress. The audit checks the actual code and work, not only the tracker.
  • One voice per stack. The Stack Leader keeps every member of their stack updated through regular meetings.
